# Інформація про зовнішні застосунки

> **Примітка (прошивка ≥ жовтня 2025):** єдиний файл `external.ld` розділено на `external_tier0.ld`, `external_tier1.ld`, `external_tier2.ld` (по одному на рівень розміру флешу пристрою); вони тепер генеруються автоматично з маркера `tier.txt` кожного застосунку скриптом `tools/update_external_tier_ld.py`. Де на цій сторінці сказано `external.ld`, читайте як `external_tier0.ld` (файл рівня 0 все ще містить усі застосунки). Не редагуйте ці файли вручну — змінюйте `tier.txt` і перезбирайте. Значення рівнів — у [Створенні простого зовнішнього застосунку](Create-a-simple-external-app).

Зовнішні застосунки схожі на внутрішні тим, що компілюються й лінкуються з рештою прошивки, але на етапі лінкування для кожного зовнішнього застосунку у файлі `external.ld` вказується фейковий діапазон адрес пам'яті. Після лінкування зовнішні застосунки вилучаються з образу прошивки й виносяться в окремі файли. Це сильно відрізняється від baseband-модулів, які компілюються й лінкуються окремо, виконуються на іншому CPU (M4) і спілкуються з основною прошивкою через протокол повідомлень. Оптимізацію LTO при лінкуванні зовнішніх застосунків застосовувати не можна — щоб лінкер не намагався ділити код між застосунками.

## export_external_apps.py

Цей python-скрипт редагує образ кожного зовнішнього застосунку, щоб:
1. замінити фейкові адреси, використані на етапі лінкування, на реальні адреси RAM, куди застосунок завантажуватиметься для виконання;
2. долучити потрібний baseband-образ;
3. додати контрольну суму для перевірки цілісності під час розпакування (untar).

### Заміна адрес

Приклад: якщо фейковий діапазон застосунку — 0xADC00000…0xADC07FFF, скрипт шукає в файлі застосунку значення в цьому діапазоні й замінює їх, _припускаючи_, що це вказівники на пам'ять усередині цього застосунку. Якщо знайдено значення, у якого старший байт — 0xAD, а наступний байт міг би бути адресою в іншому застосунку, виводиться попередження:

```
WARNING: External code address 0xadb01234 at offset 0x1000 in tetris.himg
```

Оскільки LTO вимкнено, це найімовірніше хибне спрацювання (значення може бути просто інструкцією коду чи даними). Фейковий діапазон 0xADxxxxxx обрано тому, що в образі прошивки мало значень у цьому діапазоні, і будь-яка спроба звернутися до нього спричиняє збій GURU meditation.

### Baseband-образи

Baseband-модулі зовнішніх застосунків створюються так само, як для внутрішніх, стискаються й виконуються з RAM на M4. Але їх вилучають з ROM прошивки й долучають до образу застосунку згаданим скриптом.

### Контрольна сума

Контрольна сума для файлів зовнішніх застосунків — просто uint32-сума всіх 32-бітних значень у файлі, зі зрештою інвертованим знаком, щоб загальна сума (разом із контрольною сумою) дорівнювала 0 для валідного образу. Такий простий метод обрано заради швидкості (CRC32 був би повільнішим).

## make_spi_image.py

Цей python-скрипт створює образ ROM прошивки, долучаючи baseband-образи й просту контрольну суму, а також перевіряє, що немає посилань на фейкові діапазони адрес зовнішніх застосунків. Може вивести попередження, схоже на:

```
WARNING: Possible external code address 0xadb96ef0 at offset 0xb24a4 in portapack-h1_h2-mayhem.bin
```

Щоб визначити, справжнє це попередження чи хибне, знайдіть згадану адресу серед діапазонів у `external.ld`. Наприклад, рядок `ram_external_app_lcr(rwx) : org = 0xADB90000, len = 32k` означатиме, що прошивка, можливо, звертається до пам'яті застосунку LCR. Щоб перевірити: змініть у `external.ld` адресу цього застосунку на інший невикористаний діапазон (наприклад `org = 0xADFF0000`) і перезберіть. Якщо адреса в попередженні зміниться на новий діапазон — прошивка справді звертається до коду/даних цього застосунку; якщо лишиться тією самою — це хибне спрацювання, яке можна ігнорувати.
