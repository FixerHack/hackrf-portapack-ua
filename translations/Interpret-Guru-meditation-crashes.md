# Розбір збоїв Guru meditation

Нотатки й інструменти, щоб перетворити екран guru на рядок коду й зловити два режими збоїв, невидимі під час збирання.

Задайте `ARM_TOOLCHAIN` один раз, якщо toolchain не в `PATH`:

```sh
export ARM_TOOLCHAIN=/path/to/arm-none-eabi-   # зверніть увагу на дефіс у кінці
```

Усі три скрипти також автоматично знаходять `./armbin/bin/arm-none-eabi-`.

## Читання екрана guru

`draw_guru_meditation()` друкує `r0`–`r3`, `r12`, `lr`, `pc` й іноді `cfsr`.

- **`pc`** — де програма впала.
- **`lr`** — адреса повернення функції, що виконувалася (тобто *викликач*).

`lr` зазвичай корисніший. Якщо `pc` — дике значення без символу, а `lr` виглядає розумно, це **непрямий виклик через поганий вказівник** (`blx` на пошкодженому `std::function`, застаріла vtable, перехід на нерезидентну функцію). Шукайте `lr` — він вказує місце виклику.

Рядок-підказка важливий:

| Підказка | Звідки | Означає |
|---|---|---|
| `Hard Fault` | `HardFaultVector`, `application/debug.cpp` | загальний збій, дивіться `pc`/`lr` |
| `Stack Overflow` | той самий обробник, коли `get_free_stack_space() < 16` | 4 КБ стеку M0 справді вичерпано |
| заголовок `M4 Guru` | `event_m0.cpp` | збій у baseband, не в застосунку |

`Stack Overflow` — **не** проблема купи чи фрагментації. Див. «Бюджет стеку».

## 1. Переклад адреси — guru_lookup.py

Класичний підхід:

```sh
arm-none-eabi-gdb -q -ex "x/3i 0xADDR" --batch firmware/application/application.elf
```

працює для основної прошивки, але дає нісенітницю для **зовнішніх застосунків**. Вони лінкуються за адресою-заповнювачем `0xADxxxxxx` (див. `external.ld`) й копіюються під час виконання у свій `memory_location` у локальному SRAM (близько `0x1008xxxx`). Guru показує адресу часу виконання, якої немає в ELF.

Переклад: `link_addr = section_vma + (runtime_addr - memory_location)`. `memory_location` — перше 32-бітне слово `.ppma` застосунку; VMA секції — з `objdump -h`. `guru_lookup.py` робить це за вас:

```sh
# guru показав lr 0x10085CF9, pc 0x0FF36284
firmware/tools/guru_lookup.py 0x10085CF9 0x0FF36284

# кожен застосунок завантажується за своєю адресою — звузьте, якщо знаєте
firmware/tools/guru_lookup.py --app waterfall_designer 0x10085CF9

# збій M4 — шукайте в baseband-образі
firmware/tools/guru_lookup.py --baseband adsbrx 0x10081234
```

Скрипт друкує demangled-символ, рядок коду **разом з inlined-кадрами** (`addr2line -i`, чого простий `x/3i` не дає) і вікно дизасемблювання з позначеною інструкцією збою.

> **Шукайте в точно тому бінарнику, що впав.** Адреси зсуваються при кожній збірці. Якщо ви вже перезібрали — відповідь буде впевнено неправильною.

## 2. Бюджет стеку — stack_usage.py

Стек процесу M0 — всього **4096 байтів** (`__process_stack_size__ = 0x1000` у `LPC43xx_M0.ld`). Це весь бюджет для UI-потоку, зокрема й зовнішніх застосунків — вони мають свою область коду/даних 32 КБ, але ділять цей стек. Купа — ~43 КБ, і вона рідко є проблемою.

Головна небезпека — `File`. `ffconf.h` задає `_FS_TINY 0` і `_MAX_SS 512`, тож кожен `FIL` несе 512-байтовий секторний кеш, а `File` тримає його за значенням:

| | стек |
|---|---|
| один локальний `File` | ~560 Б |
| `copy_file()` (два `File` + буфер 512 Б) | ~1784 Б |
| `Gradient::load_file()` | ~760 Б |
| `run_external_app()` (тримає `File`) | ~776 Б |
| `BufferLineReader::read_line()` | ~192 Б |

Двох-трьох вкладених локальних `File` під ланцюжком диспетчеризації UI-подій достатньо для переповнення.

```sh
firmware/tools/stack_usage.py build/firmware/application/application.elf        # найгірші
firmware/tools/stack_usage.py build/.../application.elf --grep copy_file        # одна функція
firmware/tools/stack_usage.py build/.../application.elf --chain main run_external_app copy_file f_open
```

### Чому не просто grep за `sub sp`

Thumb-1 не кодує `sub sp, #imm` понад 508 байтів, тож важливі кадри емітуються як від'ємна константа з literal pool:

```
ldr r4, [pc, #728]   ; (2e0 <...>)
add sp, r4           ; r4 = 0xfffffcfc = -772
```

Наївний grep бачить `sub sp, #24` і пропускає сусідній 772-байтовий кадр. `stack_usage.py` розв'язує літерал.

### Як уникнути переповнення

- Виносьте кожен `File` у власну функцію, щоб його кадр зникав до наступного кроку; `__attribute__((noinline))` закріплює це, якщо ланцюжок тісний.
- Не робіть файловий ввід/вивід усередині колбека, що вже на кілька кадрів углиб. `text_prompt()` і `FileLoadView` викликають ваш обробник, а *потім* `nav.pop()` — відкладіть роботу через `nav.set_on_pop()`, і вона виконається «мілко».
- Конструктори зовнішніх застосунків виконуються під `run_external_app()`, ~776 Б углиб. Не викликайте звідти `copy_file()`.

## 3. Протікання секцій між зовнішніми застосунками — check_external_symbol_placement.py

Правила в `external.ld` зіставляють **імена вхідних секцій**, а не namespace'и. Глоб на кшталт `*(*ui*external_app*level*);` також збігається з символом, чиє mangled-ім'я просто *містить* `level` (наприклад `on_add_level`). Призначення секцій — за принципом «перший збіг виграє», тож символ потрапляє в область чужого застосунку. Оскільки резидентним є лише один зовнішній застосунок, виклик переходить у незамаплену пам'ять.

Під час збирання це беззвучно, а проявляється як hard fault з диким `pc`. `export_external_apps.py` вже попереджає про *дані*-слова, що вказують на інший застосунок, але не ловить цей випадок: `bl` — PC-відносний, тож ціль ніколи не з'являється як літеральне слово.

```sh
firmware/tools/check_external_symbol_placement.py
```

Виходить з ненульовим кодом і називає проблемні символи. Варто запускати після зміни `external.ld`, додавання застосунку чи називання методу на честь наявного застосунку. Виправлення — обмежити правило власними джерелами застосунку:

```diff
-        *(*ui*external_app*level*);
+        */external/level/*(*ui*external_app*level*);
```

> `LPC43xx_M0.ld` робить `INCLUDE external.ld`. Переконайтеся, що обидва в `LINK_DEPENDS` (`firmware/application/CMakeLists.txt`), інакше редагування правил секцій не перелінкується й зміна виглядатиме як пустишка.

## Розібраний приклад

Guru показав `lr 0x10085CF9`, `pc 0x0FF36284`.

1. `pc` не розв'язується, `lr` у локальному SRAM → зовнішній застосунок, непрямий чи поза-діапазонний перехід. Шукаємо `lr`.
2. `guru_lookup.py --app waterfall_designer 0x10085CF9` → link-адреса `0xADF613DC`, це `ui_waterfall_designer.cpp:144`, лямбда `button_add_level.on_select`.
3. Дизасемблювання показало `bl ade11968` — область застосунку `level`, не `0xADF6xxxx`.
4. `check_external_symbol_placement.py` підтвердив чотири символи в неправильній області, усі з `level` у mangled-іменах.
5. Повідомлений `pc` виводиться арифметично: зсув `bl` (`-0x14FA74`) PC-відносний і переживає копіювання, тож під час виконання `0x10085CF8 - 0x14FA74 = 0x0FF36284`.

## Ручний посібник

Іноді програма «має поганий день» і просто кладе всю машину. Ми додали екран помилки для розробників, у яких немає [Black Magic Probe](https://hackrf.readthedocs.io/en/latest/LPC43XX_Debugging.html). Ви все одно зможете звузити місце помилки.

### Інформація на екрані

- Перший рядок містить найважливіше:
  - **M0** — збій у прошивці застосунку;
  - **M4** — збій у baseband-прошивці.
- Підказка (Hint) може бути: `Hard Fault` (недійсна операція, напр. доступ до пам'яті), `MemManage` (помилка пам'яті), `BusFault`, `UsageFault` або інший текст на кшталт `NoImg`, `BBRunning` (див. виклики `chDbgPanic`).
- Регістри (видимі лише при Hard Fault): `r0`–`r3` і `r12` — значення на момент збою; `lr` — адреса повернення викликача (використовуйте, лише якщо `pc` непридатний); `pc` — адреса поточної інструкції (використовуйте на наступному кроці).

### Визначення місця в коді C/C++

Виконайте, замінивши `0xd440` на ваше значення `pc`/`lr`. Для помилок M0 — `firmware/application/application.elf`; для M4 — поточний завантажений baseband-образ (напр. `firmware/baseband/baseband_adsbrx.elf`).

> На Arch при помилці `libncurses.so.5` встановіть [ncurses5-compat-libs](https://aur.archlinux.org/packages/ncurses5-compat-libs) з AUR.

```console
arm-none-eabi-gdb -q -ex="x/3i 0xd440" --batch firmware/application/application.elf
```

Або дизасемблюйте весь образ і перегляньте файл:

```console
arm-none-eabi-objdump --source firmware/application/application.elf > application.objdump
```

### Дамп стеку M0

Після збою натискання кнопки DFU покаже вміст стеку ядра M0 з гортанням. Показуються всі слова стеку, починаючи з першого використаного від вмикання PortaPack. Якщо відоме значення LR, слова стеку з цим значенням підсвічуються жовтим; слова, що можуть бути адресами в області коду, — білим.
